# Механика подбора и логика категоризации

Документ закрывает требование ТЗ: категория определяется прохождением теста, работодатель
ищет по категории и выходит на конкретного кандидата, контакты скрыты до согласия.

## 1. Категория

```text
category = специализация × грейд
backend × junior | backend × middle | backend × senior | frontend × … | qa × …
```

- Справочник категорий задаёт команда проекта (`categories` в SQLite, сид из `app/db/seed.js`).
- Категория присваивается **только** после батареи и только если `test_score ≥ cutoff`
  (см. [docs/TESTING.md](./TESTING.md)). Кандидат без теста виден в банке как
  «неподтверждённый» и всегда стоит ниже подтверждённых.
- Пересдача возможна, но не чаще раза в `GRADE_COOLDOWN_DAYS` (30 дней) по той же
  специализации; грейд при этом не режется принудительно.

## 2. Пул кандидатов для потребности

```text
потребность (specialization, grade, stack, domainText)
  → кандидаты той же категории
  → rank = 0.60·test_score + 0.15·motivation + 0.10·fsp_boost + 0.15·domain_boost
  → сортировка: сначала совпадение грейда, затем rank
  → фильтры (стек, ФСП) только сужают выдачу
```

| Компонент | Смысл |
|---|---|
| `test_score` | результат батареи, главный вклад |
| `motivation` | поведение во время мини-проекта (телеметрия, без чтения лишних данных) |
| `fsp_boost` | 1, если у кандидата есть подтверждённые достижения ФСП, иначе 0 |
| `domain_boost` | совпадение прошлых ролей/доменов с текстом потребности |

Каждая строка подборки содержит `explanation` — текстовое объяснение, почему кандидат
в этой категории и что в его ответах совпало с потребностью.

## 3. Колода и решения работодателя

- `GET /api/employer/needs/:id/deck/next` — одна карточка: категория, стек, опыт,
  объяснение, **без контактов**.
- Решения: `rejected` (отказать) и `later` (отложить). Они записываются в `need_reviews`
  и учитываются: приглашение отклонённому не отправить (409 `candidate_rejected`),
  отложенный попадает в `GET /needs/:id/deferred` и может быть возвращён в работу.
- Фильтры в подборке (`stack`, `fsp`) не меняют состав уже полученной выдачи — это
  проверяется аудитом (E-07).

## 4. Приглашение и приватность

```text
работодатель → приглашение (вилка от–до, текст оффера, канал связи)
                 ↓ status = sent
кандидат      → accept | decline
                 ↓ accept
контакты      → видны работодателю (phone, contact_email)
```

- Вилка ЗП обязательна: без `salaryFrom`/`salaryTo` приглашение не создаётся (400).
- Вакансия не требуется — приглашение создаётся по потребности.
- До accept в JSON работодателя нет ни `phone`, ни `contact_email`, а
  `GET /api/employer/candidates/:id/contacts` отдаёт 403.
- Повторное приглашение по той же потребности тому же кандидату — 409
  (`invitation_duplicate`).

## 5. Что можно расширить

| Идея | Статус |
|---|---|
| Публикация вакансий и отклик кандидата | не сделано, каталог `app/modules/vacancies/` пуст |
| Регулярные короткие задания от работодателя | механика коротких тестов есть (`employer-tests`), периодичность — в планах |
| Реальный реестр ФСП | схема адаптера описана в [docs/FSP-INTEGRATION.md](./FSP-INTEGRATION.md) |
| ATS-концепция | описана как концепция в [docs/FUNCTIONAL-COVERAGE.md](./FUNCTIONAL-COVERAGE.md) |

## Как проверить

```bash
npm run validate:matching   # M1 категория, M2 score, M3 ФСП, M4 нет контактов в matches
npm run validate:privacy    # P1–P8: контакты, согласия, токены, лимиты загрузки
BASE_URL=http://127.0.0.1:8899 node scripts/functional-audit.js   # механика end-to-end
```
