# HandCheck — презентация проекта и питч

Материал для сдачи ФСП (спец. трек 2026). Четыре слоя: **тезисы питча** (60 секунд),
**слайды** (по одному — заголовок, содержание, что говорить), **демо-маршрут** (что
показывать вживую) и **ответы на неудобные вопросы жюри**.

## 1. Пичч на 60 секунд

> HandCheck — платформа найма IT-специалистов, где категорию кандидата определяет не
> резюме, а тест. Кандидат проходит опрос и батарею заданий, получает категорию
> «специализация × грейд», и дальше инициатива переходит к работодателю: он ищет по
> категориям, а не по вакансиям, и сам зовёт кандидата с вилкой ЗП. Контакты кандидата
> не отдаются работодателю, пока кандидат не принял приглашение — это убирает спам
> откликов и даёт работодателю ответ именно на свой стек. Мы не собираем вакансии и не
> ранжируем людей по престижу резюме: мы измеряем навык и связываем его с предложением.

## 2. Слайды

### Слайд 1. Проблема

**Заголовок:** Рекрутинг решает не ту задачу

- Вакансия спрашивает «что ты написал в резюме», а работодателю нужно «кто реально умеет».
- Кандидат откликается вслепую, работодатель получает поток одинаковых анкет.
- Контакты утекают раньше, чем состоялся договор.
- Категория «junior backend» означает что угодно: от «вчера написал hello world» до
  «полгода в продакшене».

**Говорить:** это не «ещё один job board», это замена входной сценария отбора.

### Слайд 2. Решение

**Заголовок:** Категорию даёт тест, приглашение даёт работодатель

1. Кандидат проходит опрос → специализация и заявленный грейд.
2. Проходит батарею: короткие вопросы с дедлайном + мини-проект, оценка по рубрике.
3. Получает категорию = специализация × грейд. Ниже cutoff — статус «не подтверждён»,
   грейд вниз не режется.
4. Работодатель описывает потребность → получает подборку по категории с объяснением.
5. Работодатель сам шлёт приглашение с вилкой ЗП — без обязательной вакансии.
6. Контакты кандидата видны только после `accept`.

**Говорить:** инициатива у работодателя — главный критерий жюри (35%).

### Слайд 3. Почему не «одно задание на всех» и не «уникальный LLM на каждого»

**Заголовок:** Тест устойчив к утечкам и к несравнимости

- **Банк заданий:** 9 батарей (backend / frontend / QA × junior / middle / senior), у
  каждой — две параллельные формы A/B. Одинаковые вопросы всем не достаются.
- **Cutoff по грейду:** junior 0.55, middle 0.68, senior 0.78 — категория выдаётся
  только по результату, а не по самоописанию.
- **LLM — только черновики:** генерация новых заданий для работодателя, но оценка
  кандидата всегда по банку. Никакой «уникальной некалиброванной генерации» под каждого.
- **Проверяемо:** `npm run validate` — cutoff-тесты, эквивалентность форм A/B
  (разница среднего < 0.15), устойчивость к утечкам (2 формы на ячейку).

**Говорить:** это ровно тот пункт ТЗ, где чаще всего «срезают» жюри-проекты.

### Слайд 4. Подбор

**Заголовок:** Сначала категория, потом ранг

- Выдача идёт по категории из теста, а не по резюме и не по престижу школы.
- Внутри категории: `0.60 × test_score + 0.15 × мотивация + 0.10 × ФСП + 0.15 × домен`.
- Фильтры (стек, ФСП, статус) только сужают выдачу и не ломают уже полученную подборку.
- Колода показывает по одному кандидату с обоснованием; «отложить» и «отказать»
  учитываются при следующих приглашениях.

**Говорить:** неподтверждённые кандидаты видны, но всегда ниже подтверждённых — это честно.

### Слайд 5. Приватность как механика, а не как юридическая страница

**Заголовок:** Контакты появляются только после accept

- В API работодателя до accept нет `phone` и `contact_email` — ни в подборке, ни в
  списке приглашений (проверено тестами `validate:privacy`).
- Согласие на обработку данных обязательно на регистрации и на старте батареи;
  уведомление 152-ФЗ с оператором доступно публично.
- Есть механизм отзыва токена ИИ-клиента и аудит его вызовов.

**Говорить:** приватность здесь меняет поведение рынка — «отклик вслепую» становится
«приглашение с моей стороны».

### Слайд 6. Что ещё в продукте

**Заголовок:** Оценка работодателя — после accept

- Приняв приглашение, кандидат может пройти короткий тест работодателя (вопросы с
  автопроверкой), который назначается только после принятого приглашения.
- Комната звонка с записью и расшифровкой, сводка разговора.
- MCP-сервер для ИИ-клиентов: токен с согласием, аудит вызовов, изоляция от REST.

**Говорить:** это «доп. функционал» из ТЗ — 7% веса, но показывает, что система
дорабатывается вокруг основной механики, а не вместо неё.

### Слайд 7. Техника и воспроизводимость

**Заголовок:** Весь стек — 4 CPU, без GPU

- Node.js 20+ / Express, SQLite в томе, статический UI без SPA-фреймворка.
- Docker Compose, деплой по `main` через self-hosted runner, OpenAPI-контракт.
- Секреты только на сервере, `DEMO_MODE=1` даёт готовые демо-аккаунты для жюри.
- Проверки: `npm test`, `npm run validate`, `scripts/functional-audit.js`
  (41 проверка на стенде, 8 читающих проверок на проде).

**Говорить:** жюри может поднять у себя одной командой и пройти сценарий из README.

### Слайд 8. Что не сделано и почему

**Заголовок:** Честный список

- Вакансии и отклик — не блокер MVP по ТЗ, каталог пуст.
- PDF/OCR резюме — помечено в ТЗ как «позже».
- ATS-интеграции и антифрод — нужна концепция, а не код (так и в ТЗ).
- Реальный реестр ФСП API не выдаёт; сценарий «нет истории ФСП» работает.

**Говорить:** список из [FUNCTIONAL-COVERAGE.md](./FUNCTIONAL-COVERAGE.md), там же
доказательства по каждому пункту.

### Слайд 9. Демо-маршрут (≈7 минут)

1. `/` — вход, две кнопки быстрого демо-входа (работодатель / соискатель).
2. Работодатель: `/employer/deck` — колода, у карточки категория и объяснение, контактов нет.
3. Работодатель: `/employer/list` — подборка по потребности; фильтры сужают, но не ломают.
4. Приглашение с вилкой 120 000–180 000 ₽, без вакансии.
5. Кандидат: приглашение → «Принять» → статус.
6. Работодатель: контакты появились; у второго кандидата — «Отказать», контактов нет.
7. Кандидат: короткий тест работодателя после accept.

### Слайд 10. Итог

**Заголовок:** Категория, приглашение, согласие — в таком порядке

- Категорию даёт тест, приглашение инициирует работодатель, контакты — только согласие.
- Система не собирает вакансии и не ранжирует по престижу: она измеряет навык.
- Всё проверяется скриптами, а не обещаниями: `npm run validate`, функциональный аудит.

## 3. Ответы на вопросы жюри

**Почему не вакансии?** Вакансия — это объявление о намерении; категория — это
измеренный навык. Работодателю нужен ответ «кто умеет», а не «кто откликнулся».

**Как не слить сильных и слабых?** Cutoff по грейду и рубрика; ниже cutoff — статус
«не подтверждён», а не понижение грейда. Пересдача — раз в 30 дней.

**Что с утечкой ответов?** Две формы A/B на каждую ячейку батарей, лимит пересдачи,
серверные дедлайны, телеметрия попыток.

**Как защититься от недобросовестного работодателя?** Не выдавать контакты до accept,
ограничивать приглашения по пулу категории, вести аудит действий. Концепция антифрода
описана в документации.

**Сколько стоит поддержка?** Один контейнер Node + SQLite, без GPU. Основная цена
эксплуатации — LLM-генерация черновиков заданий, которая отключается флагом.

**Почему Free/LLM?** Внешние LLM используются только для черновиков заданий
работодателя. Оценка кандидата идёт по банку — воспроизводимо и без сети.
