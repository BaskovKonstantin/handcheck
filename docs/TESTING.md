# Механика тестирования и почему она устойчива

Документ закрывает требование ТЗ: «Единый набор заданий для всех не подходит… генерация
уникальных заданий нейросетью под каждого кандидата не гарантирует сопоставимость.
Придумайте и реализуйте подход, устойчивый к этим проблемам».

## Выбранный подход: банк заданий + параллельные формы + cutoff по грейду

```text
специализация × грейд  →  батарея (quick-вопросы + мини-проект)  →  рубрика  →  score  →  cutoff  →  категория
        9 ячеек                  2 равноценные формы A и B          ключи и веса   0.55/0.68/0.78
```

### 1. Банк заданий вместо генерации под каждого

- 9 батарей: `backend | frontend | qa` × `junior | middle | senior`.
- В каждой ячейке 18 заданий: 16 коротких (`quick`) + 2 проектных (`work`) — **162 задания**.
- У каждой задания есть рубрика: список ключевых выражений и веса, поэтому оценка
  воспроизводима и не зависит от того, кто и когда отвечал.
- LLM используется только для черновиков новых заданий работодателю
  (`POST /api/assessment/generate`), в банк они попадают после редакторской проверки.
  Оценка кандидата никогда не зависит от свежесгенерированного текста.

### 2. Параллельные формы A и B — защита от утечки ответов

- При старте батареи форма выбирается случайно (`form_key` ∈ {A, B}); обе формы собраны
  так, чтобы быть равноценными по сложности и рубрике.
- Проверка эквивалентности: на одном и том же наборе ответов средний балл форм A и B
  отличается на **0.00** при допустимом пороге 0.15 (`validate:assessment`, метрика A1).
- Проверка устойчивости к утечкам: серия стартов показывает обе формы в каждой ячейке —
  **9 из 9** (`scripts/assessment-metrics.js`, метрика `leakageResistance`).
- Пересдача ограничена: `GRADE_COOLDOWN_DAYS` (по умолчанию 30 дней) на специализацию,
  поэтому «выучить ответы» невыгодно.

### 3. Честная категоризация, а не принудительное понижение

| Параметр | Значение |
|---|---|
| `test_score` | `0.6 × knowledge + 0.4 × breadth`, где `knowledge = 0.5 × quick + 0.5 × work` |
| Cutoff junior | 0.55 |
| Cutoff middle | 0.68 |
| Cutoff senior | 0.78 |
| Ниже cutoff | статус `unconfirmed`, категория не выдаётся, грейд **не понижается** |
| Выше cutoff | категория «специализация × грейд» фиксируется в `candidate_categories` |

Измеренные значения на эталонных ответах (`context/metrics-assessment.json`):

| Ответы | `test_score` | Итог против cutoff middle (0.68) |
|---|---|---|
| Сильные (эталон middle) | 0.734 | подтверждено |
| Слабые (эталон middle) | 0.000 | не подтверждено |
| Форма A / форма B (эталон) | 0.812 / 0.812 | Δ = 0.00 |

### 4. Технические ограничения, которые делают замер честным

- **Серверный дедлайн.** Таймер живёт на сервере (`opened_at` + тип задачи), клиент показывает
  остаток, полученный от сервера. Перезагрузка страницы не продлевает время.
- **Пошаговость.** Пропустить шаг нельзя: `not_current_task`.
- **Черновик.** Ответ сохраняется до отправки (`PATCH /tasks/:id/draft`), при `pagehide`
  отправляется через `sendBeacon`.
- **Телеметрия попыток.** События `open/blur/focus/paste/draft/submit` пишутся в
  `attempt_events` и влияют на метрику `integrity`; в выдачу работодателя она не отдаётся.
- **Утечки нет.** Ответ на последнем шаге не содержит `test_score` — проверяется
  автотестом A4 в `validate:assessment`.

## Где это в коде

| Что | Файл |
|---|---|
| Выдача батареи, формы, шаги | `app/modules/assessment/router.js` |
| Скоринг, cutoff, категория | `app/modules/assessment/service.js`, `app/lib/rubric-score.js` |
| Дедлайны и целостность | `app/lib/attempt-timer.js`, `app/lib/attempt-integrity.js` |
| Банк заданий и сид | `app/db/battery-catalog/*`, `app/db/task-battery-content.js` |
| Проверки | `scripts/validate-assessment.js`, `scripts/assessment-metrics.js` |

## Как проверить

```bash
npm run validate:assessment          # A1–A4: эквивалентность, cutoff, отсутствие утечек
METRICS_JSON=context/metrics-assessment.json node scripts/assessment-metrics.js   # числа для отчёта
```
